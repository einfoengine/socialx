## 1. What socialX is

A productized social media content service sold on a monthly retainer, built only for
HighLevel SaaS resellers. Prewritten posts are targeted at real HighLevel features,
customized per client, and delivered scheduled into the client's HL Social Planner.

It is not an agency and not a freelancer marketplace. Pick a tier, complete onboarding,
the feed runs.

## 3. The buyer

### One line

The founder or CEO of a white-label HighLevel SaaS reseller, $5k to $50k MRR, team of one
to ten, US / Canada / UK / Australia, actively selling with paying clients, who knows
their own feed is costing them deals.

### The persona: Nathan Cole (fictional composite, never published as a real customer)

34, Tampa. Ex local agency, flipped to SaaS mode 18 months ago. Sells rebranded HighLevel
as FlowStack Pro to roofing and HVAC at $297/mo. 38 subaccounts, roughly $11k MRR. Team is
Nathan, one VA, one part-time setter. Sells on Zoom demos from Facebook groups and
referrals.

> "My platform replaces five tools and runs half their business. My Instagram has four
> posts from last year. Prospects see the second thing before they ever book the demo."

**Usage rule:** every socialX asset gets written to one reader, and that reader is Nathan.
If a draft reads as written for an audience, rebuild it.

### Segments and tier mapping

| Segment | Signals | Tier |
|---|---|---|
| The Launcher | Under $10k MRR, credibility over depth | Starter $197 |
| The Operator | $10k+ MRR, wants the feed to sound like them | Growth $397 (the core) |
| The Scaler / hybrid | $25k+ or growth mode, daily presence, four channels | Scale $597 |

### The wedge: the trust gap

Prospects research the brand before booking a call. A dead feed tells them this is not a
serious SaaS. The deal dies at the trust stage, before the demo, and the founder rarely
sees it happen. Every message ladders back to this.

Ranked pain, the top four are the deployed cards on the live site and the language is
locked:

1. No time, no system. Kills consistency.
2. DIY kills positioning. Caps the price ceiling.
3. Generic SMM does not speak HighLevel. Wastes the spend.
4. Freelancer chaos. Burns founder hours.
5. Feature blindness. Undersells the product.
6. The embarrassment tax. Removes proof from the motion.

### Belief system to write against

Nobody in this ICP needs convincing that a dead feed looks bad. The blocker was never
belief, it is friction and the hiring assumption. Attack the friction, never the belief.

### Anti-ICP (who socialX refuses)

- Large agencies wanting custom strategy retainers. Route them to growX.
- Non-HighLevel shops. The library is HL-native.
- Micromanagers who want to art-direct every post.
- Buyers wanting SMM for their end clients. That is the future white-label tier. Waitlist.
- Hobbyists without a live offer.
- One-off bargain hunters. Published pricing filters them by design.

## 4. Differentiation

- **HighLevel-only.** Every library post is built around a real HL feature.
- **Library plus a customization ladder.** Brand swap on Starter, full rewrite on Growth,
  bespoke on Scale.
- **Scheduled, not delivered.** Lands in the client's HL Social Planner through restricted
  content-manager access, not a zip file.
- **Productized flat pricing.** Three published tiers, self-serve checkout, no discovery
  call gate.
- **Built by the team behind GHL Video.**
- **Speed.** First batch in 5 to 7 days.

**Sibling logic:** socialX is the productized wedge. growX is full-service bespoke.
socialX never drifts into custom-agency scope, media buying, or strategy retainers.

## 5. Operating model and roadmap

Four stages: content production, marketing, sales and onboarding, fulfillment.

**Library rules.** Five pillars with a default monthly mix: Feature Spotlight 30%,
Education 25%, Pain Agitation 18%, Social Proof 15%, Promotional 12%. Library defaults are
niche-neutral; niche enters only at customization. growX CRM (growxcrm.com) is the one demo
brand and it is real. OmniHub is retired. Phase 1 of the library covers 285 posts plus 30
motion scripts across all 27 HighLevel features.

**Fulfillment phases.**

| Phase | Clients | State |
|---|---|---|
| Phase 1 | 0 to 25 | Manual ops: ClickUp, Drive, Canva, manual HL scheduling. **Current phase.** |
| Phase 2 | 25 to 100 | Internal web app for library browsing and batch assembly |
| Phase 3 | 100+ | Full white-label client portal: approval flow, template-variable customization, direct HL Social Planner API integration |

**The portal is socialX's long-term moat.** Note that the live FAQ already references a
"socialX dashboard" and a "customer portal" that do not exist yet.

### Stack

HighLevel is the CRM, dogfooded end to end (Setter and Closer pipelines, a nine-stage
delivery and retention pipeline, checkout abandonment on Order Form Submission). ClickUp is
the ops backbone only. All communication runs in Slack. Files in Drive, visuals in Canva
and Figma, docs in Notion or Google Docs, billing via Stripe or HL Payments, outbound via
Apollo and Instantly.

## 6. Voice and copy law

Direct, outcome-focused, founder to founder. The reader is a HighLevel SaaS founder, so
SaaS economics are never explained.

**The copy law, locked:** customer-first hook opening on the reader's world, the HL feature
as the quiet resolution in a dedicated middle beat, then the outcome, then one CTA. Never
lead with the product.

Strict rules:

- **Zero em-dashes** across every asset, internal or public. En-dashes, middots, and
  ellipsis characters are out too.
- Exact casing: socialX, growX, GHL Video, HighLevel, HL.
- No SaaS-101 explanations. MRR, CAC, LTV, churn are assumed knowledge.
- Library defaults stay niche-neutral.
- Contractions are fine. This differs from GHL Video's stricter rules.
- No generic CTAs. Name the action.

Words that repel: agency-speak, "affordable" or "cheap" (triggers the Fiverr scar),
explaining SaaS terms, hype and exclamation energy, algorithm-chasing talk, generic CTAs
like "learn more", and any implied HighLevel affiliation.

## 10. Codebase map

Next.js 16.2.6 (Turbopack), React 19.2.4, Tailwind v4, TypeScript. Package manager
is **pnpm**, not npm.

Two independent projects. Separate package.json, separate node_modules, separate
install. No workspace, no root package.json, and no code shared between them.

```
portal/    the product: client portal, operator console, /api/v1
site/      socialX's own marketing website, a consumer of that API
docs/      this file and the integration policy
```

The only connection is HTTP. The site reads its copy, pricing and brand from the
portal's public API with a scoped key, through `site/lib/platform.ts`, exactly as
any customer's own website would. Nothing imports across the boundary.

### portal/

```
app/
  admin/          operator console, gated by the section permission matrix
  portal/         the client's own screens: approvals, calendar, billing, team
  api/v1/         the integration surface: content, catalog, orders, site, me
  api/internal/   scheduled work, shared-secret auth, not versioned
  (auth)/         login, callback, post-login, logout
components/       shared UI for both portals
db/
  migrations/     numbered SQL, applied in filename order
  seed/           catalogue and pricing, asserts the numbers
  tests/          each file rolls itself back
lib/
  core/
    config.ts     runtime configuration, env or config file, no build-time reads
    db/           sql.ts (tagged templates), pool.ts, actor.ts (RLS identity)
    auth/         password hashing, the owner account
    setup.ts      first-run gate and the boot token
    sites.ts      the site registry record and brand parsing
    webhooks.ts   signing, emitting, delivering, retrying
    stripe.ts, payments.ts, ratelimit.ts, urls.ts
  dal/            the authorization boundary: session, permissions, scoped
  api/            /api/v1 front door: keys, scopes, auth, cron
  sites/          resolving which site a request belongs to
scripts/          db.mjs, seeding, key minting, integration tests
proxy.ts          cookie refresh and an optimistic redirect. Not authorization.
```

### Running it

Each project separately, from inside its own folder.

```bash
cd portal && pnpm install && cp .env.example .env.local && pnpm db:migrate && pnpm dev
cd site   && pnpm install && cp .env.example .env.local && pnpm dev
```

Portal on 3001, site on 3000.

### Database posture

Plain PostgreSQL 13 or later. Supabase is one option among several rather than a
requirement: `0000_bootstrap.sql` supplies `auth.users`, `auth.uid()` and the
PostgREST role names when absent, so the whole migration set applies to a stock
Postgres.

Two things the schema cannot enforce and that a deployment must get right:

1. Connect as `portal_app`, never a superuser. Postgres exempts superusers from
   row level security silently, so tenant isolation stops working with no error.
2. Every scoped read runs inside `asActor()`, which sets the caller's identity
   transaction-locally. Outside it a query returns zero rows rather than every
   row, so a forgotten wrapper is a visible bug and not a leak.

### Migration in progress

The portal is being moved off Supabase, incrementally, with both paths reaching
the same database so the app keeps working throughout.

Done: runtime config, connection pool, SQL layer, portable RLS, local auth
schema, the whole migration set applying to plain Postgres.

Not done: roughly 320 queries still use `supabase.from()`, authentication is
still GoTrue, storage is still a Supabase bucket. New code should use
`lib/core/db` and must not add `supabase.from()` call sites.

`AGENTS.md` warns that this Next.js version has breaking changes from older
training data. Read `node_modules/next/dist/docs/` before writing framework code.
