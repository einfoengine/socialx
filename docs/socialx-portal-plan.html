[ Phase 3, the moat ]

Own the checkout. Own the delivery.

socialX runs on manual assembly in ClickUp and a checkout that lives inside HighLevel, which caps the business at roughly 25 clients. This plan replaces both with a Stripe checkout on socialX's own domain, an Admin Portal that runs delivery end to end, and a Client Portal that makes the promises already printed on the live site true.

[ Why now ]

Two things are already broken.

This is not a greenfield ambition. Both problems are live on the site today, and both get worse with every client added.

  • The site already promises a portal that does not exist. The FAQ tells clients they approve batches in a socialX dashboard and manage their subscription from a customer portal. Today there is neither. The copy is describing this plan.
  • socialX has no first-party record of its own orders. Checkout sits in HighLevel, so provisioning, entitlements, and delivery state all begin in a system socialX does not own. Every downstream rule, including the locked tier specs, depends on data living somewhere else.
What the plan does not touch

The offer, the pricing, and the ICP are unchanged. Tier specs stay locked at $197, $397, and $597. This changes how the business delivers what it already sells, not what it sells. The white label end client tier stays on the horizon and is never pitched as available now.

[ System shape ]

One app, three route groups, three layers of authorization.

The marketing site, Client Portal, and Admin Portal live in one Next.js app, sharing the design system, the session, and one deploy. What separates them is not three codebases, it is where the authorization checks sit.

Stack

DatabaseSupabase Postgres, row level security on every tenant table

[ Checkout ]

The webhook provisions the account, not the redirect.

Checkout moves to socialx.studio on Stripe. Two mechanics in this flow are worth being deliberate about, because getting either wrong is expensive later.

Webhooks handled

EventAction
checkout.session.completedProvision org, subscription, user invite, first batch shell
customer.subscription.updatedSync status, period dates, plan or cycle change
customer.subscription.deletedMark canceled, churn the org at period end
invoice.paidStore invoice, clear any delivery hold
invoice.payment_failedSet past due, start dunning, flag in admin

Plan changes and dunning

  • Upgrade is immediate with proration, but new entitlements apply from the next batch, never the batch already in production.
  • Downgrade and cancel take effect at period end, so paid work is always delivered.
  • Past due escalates: client banner on day 0, admin flag on day 3, delivery hold on day 7. Nothing gets scheduled for an account on hold, which stops socialX publishing work it has not been paid for.
  • Cards and invoices go through the Stripe Billing Portal, so socialX never handles card data.
Decide before the first Stripe subscriber

The launch rate card is temporary, but a Stripe subscription keeps whatever price it was created on. Are launch buyers grandfathered at 30, 40, and 50 percent off forever, or do they roll to the regular card at renewal? It changes the rate card model, and it is far cheaper to answer now than to unwind after real subscribers exist.

Three modelling decisions worth defending

  • Entitlements are a table, not constants in code. Post counts, platform caps, revision rounds, and turnaround days are the actual contract. One row per plan means the batch builder computes quota, the client portal shows what is used, and Starter's single revision round is enforced instead of remembered.
  • The copy law is structural. Hook, middle beat, outcome, and CTA are separate columns rather than one body field. The customer first structure is the product's quality rule, so making it four fields makes it reviewable and makes a draft that leads with the product visible at a glance.
  • Template versions are immutable, and posts point at a version. This is the only way to answer "which live client posts are running stale copy" after HighLevel ships a feature change. Feature tags cross all pillars as an independent axis, so one query finds every affected template and a second finds every affected client post.
Quota is snapshotted, not read live

A batch copies its quota from entitlements at creation time. A mid cycle plan change therefore cannot silently rewrite the terms of a batch already in production, which is a dispute waiting to happen in any system that reads the current plan at render time.

Behaviours that matter in the builder

  • Quota is live and blocking. A Growth batch cannot exceed 16 posts or 2 motion videos. The cap is not a warning.
  • Pillar mix is shown against target (30, 25, 18, 15, 12) as guidance rather than a hard block. Drift is a quality signal ops should see while assembling, not discover afterwards.
  • Templates already used by that client are flagged, so the same base post never lands twice on one feed.
  • Customization depth follows the plan. Starter exposes brand swap fields only. Growth opens full rewriting. Scale allows writing from scratch with no template link at all.

The approval screen is where the tier promise holds or breaks

Show the round counter before it is spent, not after. "Round 1 of 2" on Growth, "1 round included" on Starter, "unlimited" on Scale. The Company Profile is explicit that Starter must never be oversold as bespoke, and this screen is where that either stays honest or quietly stops being true. Every state change is logged and visible to both sides, which is what ends disputes about what was approved.

[ Sequence ]

Five releases, each shipping something usable.

Estimates assume one experienced full stack developer, and they are ranges rather than commitments. The ordering is not arbitrary.

R0

Foundations

Supabase project, core schema, RLS helpers and policies, Supabase Auth wired into Next 16, proxy.ts optimistic checks, the Data Access Layer, route groups, and admin and portal shells reusing the existing design tokens.

Done whenA staff user reaches an empty admin shell, a client user cannot, and a cross org read test fails as designed.
1 to 2 weeks
R1

Checkout and provisioning

Stripe catalog seed script, checkout server action, idempotent webhook handler, provisioning, the native onboarding wizard replacing the embedded HighLevel survey, and the admin Orders, Subscriptions, Clients, and Settings screens.

Done whenA real card buys Growth quarterly on socialx.studio, the org and subscription exist in Supabase, onboarding completes, and the order appears in the admin queue.
2 to 3 weeks
R2

Library and batch builder

Library CRUD with versioning and feature tagging, asset uploads, batch generation from subscription periods, the builder with quota enforcement, calendar assignment, manual publishing receipt, the Today dashboard, and the audit log.

Done whenA full month of client work runs end to end in the portal with no ClickUp involvement.
3 to 4 weeks
R3

Client portal

Overview, calendar, approvals with revision round enforcement, post detail with comments, billing self serve through the Stripe Billing Portal, brand profile editing, asset uploads, and team invites.

Done whenA client approves a batch and requests a revision without sending a single email.
2 to 3 weeks
R4

HighLevel automation

OAuth per location with encrypted tokens, publish jobs with retries and backoff, status reconciliation so a post edited inside HighLevel does not leave the portal claiming it is live, feature change mass update tooling, and a per client fallback to manual.

Done whenApproved posts appear in the client's HL Social Planner with no human step.
2 to 3 weeks
